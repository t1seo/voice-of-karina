# 짧은 한국어 음성의 끝맺음과 참조 품질 개선

이 문서는 두 가지 제보를 어떻게 조사하고 개선했는지 정리합니다.

- “작업이 끝났어요. 확인해 주세요.”의 끝말이 “확인해 주…”처럼 잘리는 문제
- “확인이 필요해요. 잠깐 봐 주세요.”의 시작 잡음과 어눌하게 들리는 문제

첫 번째는 **생성 결과를 검사하고 다시 생성하는 로직**, 두 번째는 **합성에 넣을 참조 발화를 고르고 검증하는 로직**을 개선했습니다. 출력 끝에 무음을 덧붙이거나 시작 자음을 잘라내는 방식으로 처리하지 않았습니다. 자동 검사의 통과와 사람이 듣기에 자연스러운지는 서로 다른 판단입니다.

## 1. 먼저 원본 합성과 재생 포장을 분리합니다

문제가 있는 공개 WAV를 보존하고, 그 WAV를 넣은 MP4를 다시 디코딩해서 비교했습니다. 확인 요청 샘플은 두 신호의 전체 상관계수가 0.99994이고 시간 지연이 0이었습니다. 처음 600 ms의 음량 차이도 약 0.006 dB였습니다. 따라서 영상 인코딩이 원래 없던 시작 잡음을 만들었다는 설명은 이 사례에 맞지 않았습니다.

조사 기준이 된 WAV의 SHA-256입니다.

| 사례 | 기존 WAV SHA-256 |
| --- | --- |
| 작업 완료 끝말 | `4ec5ec0bee2ba054c682048cce5d8684b8962191e8630cd51a1da5f61ea0d0c9` |
| 확인 요청 시작 부분 | `2c7301953beb4d183d4972dae14d1374f7be3e3b7acd9405b098c35df17fa640` |

끝말 문제의 WAV는 [회귀 테스트 파일](../tests/fixtures/truncated-ko-done.wav)로 남겼습니다. 공개 샘플의 입력, 모델 버전, 해시와 검사 결과는 [provenance.json](../assets/samples/provenance.json)에 기록합니다.

## 2. 끝말: ASR이 맞췄다고 완전한 발음은 아닙니다

기존 작업 완료 음성에는 이미 약 67 ms의 무음이 있었습니다. 그런데 Whisper는 전체 파일뿐 아니라 끝부분만 읽어도 요청한 문장을 정상적으로 전사했습니다. 무음 길이와 전사 일치만으로는 잘린 모음을 잡지 못했습니다.

현재 `speech-completeness-v2` 검사는 다음 증거를 함께 사용합니다.

1. 디코딩 가능 여부, 실제 음량, 길이, 클리핑을 검사합니다.
2. 한국어 받침 없는 모음으로 끝나는 요청은 10 ms 단위 에너지로 실제 발화 끝의 감쇠를 측정합니다. 끝에 붙은 무음 너머로 발화 끝을 찾고, 상대 음량을 사용합니다. 18 dB 이상 급격히 떨어지면서 감쇠가 40 ms보다 짧으면 재생성을 요청합니다.
3. 띄어쓰기와 문장부호를 제외한 요청 끝 네 글자가 전사 끝과 맞는지 별도로 확인합니다. 전체 문자 오류율의 기본 상한도 0.15입니다.
4. 생성 토큰 한도에 도달한 출력은 완료로 간주하지 않고, 불완전한 WAV를 성공 결과로 게시하지 않습니다.

전사가 없거나 불확실하면 미검증 상태입니다. 음향 검사는 음소 인식기가 아니어서 자연스럽게 짧은 끝말도 거부할 수 있습니다. 그래서 재시도는 문장당 기본 2회, 최대 3회로 제한하고, 무조건 통과할 때까지 작업을 새로 만들지 않습니다.

실제 교체 과정에서는 첫 결과가 2.08초였지만 감쇠가 0 ms여서 거부되었습니다. 두 번째도 2.08초였고 감쇠가 80 ms여서 통과했습니다. **길이를 늘린 것이 아니라 같은 길이의 다른 합성을 검증해 선택한 결과**입니다. 기존 불량 파일에 1초 무음을 붙여도 거부되고, 음량을 바꾼 불량 변형 22개와 정상 변형 21개도 별도로 확인했습니다.

오래된 검사 결과를 현재 정책의 통과로 취급하지 않습니다. `status`는 재검증 필요를 안내하고, `resume`는 기존 파일을 재검사한 뒤 원래 남은 횟수 안에서만 재생성합니다. 이미 통과한 다른 문장과 저장한 목소리는 보존합니다.

## 3. 시작 부분: 자음과 잡음을 섣불리 구분하지 않습니다

확인 요청 샘플의 처음 약 30 ms는 작은 신호이고, 약 30–130 ms는 비주기적인 신호에서 모음으로 이어집니다. 한국어 “확”의 `ㅎ`도 이런 특성을 가질 수 있습니다. 비교한 정상 한국어 자음 가운데는 이 샘플보다 고주파 성분이 더 큰 경우도 있었습니다.

따라서 “첫 고주파 구간을 삭제”, “VAD가 음성이 아니라고 한 부분을 삭제”, “스펙트럼 평탄도가 높으면 잡음으로 거부” 같은 규칙은 채택하지 않았습니다. 또 이 불량 제보 파일은 ASR 문자 오류율이 0이고 단어별 확률도 높았습니다. ASR 확신도를 높이는 것만으로 어눌한 발음을 해결했다고 말할 수 없습니다.

대신 합성의 입력인 참조 발화를 조사했습니다. 기존 참조는 11.346초 동안 여러 문장이 이어지고, 전사에도 불확실해 보이는 단어가 있었습니다. 음색을 보존하면서 배경·발화 전환·전사 불일치의 영향을 줄일 수 있는 짧은 발화를 비교 대상으로 삼았습니다. 이것은 참조 길이가 항상 짧을수록 좋다는 규칙은 아닙니다.

## 4. 참조: 실제 쉼 구간에서 자르고 다시 전사합니다

새 분석 흐름은 원본 대안을 남기면서 짧은 후보를 추가로 제안합니다.

1. 최초 전사의 시간 정보와 신뢰도를 확인합니다. 순서가 뒤집히거나 겹치거나 파일 범위를 벗어난 구간은 세분화하지 않습니다.
2. 여러 전사 구간이 있는 후보에서 각 발화 주변의 실제 쉼을 찾습니다. 참조 경계 전용으로 16 kHz 신호에 WebRTC VAD mode 3을 10 ms 단위로 연속 적용합니다. 세 판정 중 하나라도 음성이면 해당 30 ms 프레임은 음성으로 봅니다. 여기에 음량 조건을 함께 적용하고 연속된 두 조용한 프레임이 있어야 경계를 제안합니다. 전체 발화 비율을 계산하는 기존 감지기는 그대로 둡니다.
3. ASR 경계에서 최대 0.45초 안을 찾되 발화 여유를 남기고, 참조 길이는 3–15초로 제한합니다. ASR 타임스탬프를 그대로 잘라 쓰지 않습니다. 실제 조사에서도 ASR 끝 시각 이후에 음성이 남아 있었습니다.
4. 합성용 파일은 **원래 샘플레이트의 PCM**에서 잘라냅니다. 16 kHz 변환은 분석과 전사에만 사용하며, 잡음 제거·EQ·페이드는 적용하지 않습니다.
5. 짧게 자른 후보를 별도 배치로 다시 전사합니다. 신뢰도와 시간 정보가 유효하고, 원래 의도한 구간의 문구와 일치할 때만 우선 추천합니다. 재전사 대상은 최대 4개입니다.
6. 안전한 쉼을 찾지 못하거나 재전사가 실패하면 기존 후보로 돌아갑니다. 기존 화자 확인 요구를 그대로 유지합니다. 최종 목록은 최대 4개이며, 짧은 후보가 있어도 원래 후보를 최소 1개 남깁니다.

반환되는 `pause_bounded`는 이 절차를 거쳤다는 뜻입니다. 단일 화자임을 확인했다거나 잡음이 전혀 없다는 의미는 아닙니다. 새 참조를 저장할 때는 실제 원본 URL·시간·파일 해시·전사·준비 방법을 기록합니다. 기존 저장 목소리를 몰래 교체하지 않습니다.

새 참조 분석에는 재전사 비용이 추가됩니다. 저장한 목소리를 재사용할 때는 이 분석을 반복하지 않습니다. 분석을 더 하는 대신 반복 생성에서 더 단순하고 검증된 입력을 사용할 수 있게 하는 선택입니다.

새 분석 요청에는 변경된 캐시 식별자를 사용합니다. 기존 작업을 이어서 실행하면 기존 요청·참조·시도 횟수를 유지합니다. 개선된 참조로 바꾸려면 새 분석에서 후보를 선택하고 별도 목소리로 저장합니다.

실제 참조로 검증하면서 경계 감지의 해상도도 수정했습니다. 기존 30 ms 감지에서는 약 120 ms짜리 낮은 에너지의 쉼을 앞선 발화의 연속으로 분류해 짧은 후보를 놓쳤습니다. 연속된 10 ms 판정에서는 이 쉼과 바로 다음 발화 시작을 구분할 수 있었습니다. 프레임마다 감지기를 초기화하거나 음성을 뒤집는 우회는 채택하지 않았습니다.

## 5. 하나씩 바꾸는 비교 실험

Apple M1 16 GiB에서 같은 모델·전사·메시지를 사용하고, 시드 `20260920`, `1`, `42`를 짝지어 비교했습니다. MLX Audio는 0.5.4, Qwen3-TTS 1.7B Base 4-bit 모델 리비전은 `37e955a1deb861c088ae5f3a67043185f3d1a60c`입니다. 실제 동작하는 샘플링 기본값인 temperature 0.9, top-p 1.0, top-k 50을 유지했습니다. 시드는 실험에서 MLX 난수 생성기에 지정했으며 일반 생성 API의 보장으로 추가하지 않았습니다.

| 참조 조건 | 끝맺음 검사 통과 | 관찰 |
| --- | --- | --- |
| 기존 11.346초 참조 | 2/3 | 기존 조건의 재생성도 결과가 달라짐 |
| 같은 참조의 끝 경계만 정리 | 0/3 | 마지막만 잘라내는 방식은 개선 근거가 되지 못함 |
| 완결된 마지막 발화 약 3.052초 | 3/3 | 세 시드 모두 첫 20 ms의 상대 신호가 감소 |

짧은 발화 조건에서는 첫 20 ms의 RMS를 발화 본체의 기준 RMS로 나눈 상대 레벨이 같은 시드의 기존 참조보다 각각 17.41, 17.39, 37.36 dB 낮았습니다. 기준 RMS는 최대 프레임보다 40 dB 이내인 10 ms 프레임들에서 구한 90백분위 값입니다. 이 수치는 **초기 저레벨 신호에 한정된 결과**입니다. 사용자가 들은 30–130 ms 전체가 잡음이었다거나 발음이 완벽해졌다는 증거로 확대하지 않습니다.

보조 평가로 [Microsoft DNSMOS](https://github.com/microsoft/DNS-Challenge/blob/591184a9fcb2cbdec02520fed81a32bbbf9d73ff/DNSMOS/dnsmos_local.py)의 배경 품질 점수도 비교했습니다. 짧은 참조가 세 시드 모두 더 높았지만 전체 품질 점수는 2/3에서만 좋아졌습니다. 짧은 클립을 반복해 입력하는 평가 방식이며 한국어 음소 정확도나 인물 유사성을 측정하지 않습니다. 제품 의존성이나 자동 합격 기준으로 넣지 않았습니다.

temperature를 0.65로 낮추는 실험에서는 일부 배경 점수가 좋아졌지만 끝말이 불안정해졌습니다. 짧은 참조로 확인 요청·작업 완료·작업 시작을 비교한 7쌍에서 기본값은 끝맺음 검사를 7/7 통과했고, 낮춘 값은 4/7 통과했습니다. 전사 일치만으로 이 차이가 드러나지도 않았습니다. 따라서 기본값을 유지했습니다.

샘플 수가 작고 같은 참조에서 나온 결과이므로 모든 영상·언어·목소리에 대한 성능 보장은 아닙니다.

## 6. 자동 통과 후에도 검토 거절을 반영합니다

개선된 실제 스킬의 자동 분석은 원래 참조 안의 8.13–11.13초, 정확히 3초인 후보를 찾고 재전사로 확인했습니다. 그러나 이 참조로 생성한 첫 2.4초 출력은 문장·끝맺음 검사에 통과했어도 별도 비교에서 개선 근거가 부족했습니다. 기존 공개 파일보다 선행 20 ms 상대 에너지가 약 17.95 dB 높았고, 보조 DNSMOS 배경·종합 점수가 각각 약 0.88·0.53 낮았습니다. 이 점수는 청취 판정이 아니지만 개선됐다고 공개할 근거도 되지 못했습니다.

이 사례를 반영해 **명시적인 검토 거절 → 같은 작업 재개**를 구현했습니다.

- `reject`는 작업·문장·정확한 파일 SHA-256·사유를 받습니다. 자동 검사 당시의 음성·검사 결과를 별도 거절 기록으로 보존합니다.
- 거절을 먼저 저장하고 `resume`에서 원래 남은 횟수만 사용합니다. 문장·참조·다른 정상 결과를 바꾸지 않습니다.
- 같은 거절 요청의 재전송은 추가 작업을 만들지 않습니다. 현재 파일과 맞지 않는 다른 해시는 거부합니다.
- 거절된 바이트는 다른 파일명이나 중단된 작업의 산출물에서 발견되어도 다시 통과하지 못하며 알림 설치에서도 제외됩니다.
- 설치의 상태 확인부터 파일 복사·설정 반영까지 검토·생성과 같은 작업 잠금을 유지합니다. 동시 변경은 `job_busy`로 거부되므로 거절 이전의 상태를 읽어 뒤늦게 설치하는 경합을 막습니다.
- 생성 배치마다 새 번호의 폴더를 만들고 복구는 번호가 큰 배치부터 확인합니다. 문장별 시도 횟수가 달라도 이전 거절 파일을 덮어쓰지 않습니다. 배치 번호와 문장별 생성 예산은 별개입니다.
- 재개한 실제 작업의 두 번째·세 번째 출력은 끝맺음 검사에서 거부되었습니다. 이 작업은 총 3회 후 실패로 종료했으며 횟수를 초기화하지 않았습니다.

자동 추천 참조는 통제 실험의 3.051958초 참조와 경계·PCM이 다릅니다. 짧은 참조라는 이유만으로 실험의 이점을 그대로 적용할 수 없음을 확인한 사례입니다. 이 기능은 자연스러움을 자동 판별하는 새 모델이 아니라, 자동 검사에서 놓친 문제를 후속 검토와 대화에 반영하는 기능입니다.

관련 구현: [검토 거절](../src/voice_of_karina/workflow_review.py), [복구·재생성](../src/voice_of_karina/workflow_generation.py), [반복 요청·복구·예산 회귀 테스트](../tests/test_review_retry.py).

## 7. 공개 샘플의 선택과 한계

교체한 확인 요청 음성은 이번 조사에서 **고정 시드 통제 실험으로 생성한 기존 결과**를 현재 출력 검사로 다시 확인한 샘플입니다. 위 자동 추천 작업이 성공한 결과로 표시하지 않습니다. 새 추론을 추가하거나 실패한 작업의 횟수를 초기화하지 않았습니다.

- 참조: 기존에 저장해 둔 인터뷰 원본 PCM의 `[386357:532851]` 구간, 48 kHz에서 3.051958초. 원본 YouTube 시각으로 약 24.419104–27.471063초입니다. 새 다운로드는 403으로 거부되어 해시가 확인된 기존 녹음을 사용했습니다.
- 참조 문구: “오늘 재밌는 시간 함께 보내봅시다”. 자른 파일을 다시 전사해 확인했습니다.
- 생성: 시드 `20260920`, temperature 0.9, top-p 1.0, top-k 50. 네이티브 24 kHz PCM16 결과이며 추가 무음·페이드·잡음 제거·시간 늘리기가 없습니다.
- 보조 평가: 기존 공개 음성의 DNSMOS 배경·종합 점수 약 3.702·2.950에 비해 선택한 샘플은 약 4.007·3.240입니다. 길이가 다른 짧은 클립을 반복 입력한 결과이므로 청감과 한국어 발음의 개선을 보증하지 않습니다.

정확한 파일 해시와 재검사 결과는 [샘플 출처](../assets/samples/provenance.json)에 남깁니다. 이는 실제 로직 개선인 참조 후보 제안·독립 재전사·검토 후 재생성과 별도로, 출처가 명확한 예제를 공개한 것입니다.

## 8. 다음 품질 문제를 조사하는 순서

1. 제보된 원본 WAV와 재생용 파일을 해시와 함께 보존합니다. 재생 인코딩 문제인지 원본 합성 문제인지 먼저 나눕니다.
2. 문장 전체 전사, 끝말, 실제 파형, 참조 전사와 경계를 함께 봅니다. 하나의 지표로 자연스러움을 대신하지 않습니다.
3. 고정된 시드와 입력으로 변수 하나씩 바꿉니다. 실패한 결과도 집계하고 다른 문장으로 끝맺음 회귀를 확인합니다.
4. 실제 신호를 사용하는 실패 테스트를 먼저 만들고 수정 후 통과를 확인합니다. 시간 범위, 불확실한 전사, 전사 불일치, 원본 보존, 샘플레이트와 출처를 검사합니다.
5. 대화 스킬의 실제 `analyze → generate → status` 경로로 제보 문장을 재생성합니다. 검토에서 거절하면 `reject → resume`로 원래 남은 예산만 사용합니다. 실패 결과를 성공으로 바꾸지 않고, 공개 예제가 별도 실험에서 나온 경우 명시합니다.
6. WAV와 MP4의 전체 길이·끝부분을 확인하고 GitHub README의 실제 플레이어를 끝까지 재생합니다. 이미지와 후원 링크도 확인합니다.

로컬 회귀 검사는 다음 명령으로 실행합니다.

```bash
uv run --locked --no-sync pytest
uv run --locked --no-sync ruff check .
uv run --locked --no-sync ruff format --check .
uv run --locked --no-sync basedpyright
```

자동 검사는 실패를 줄이는 방어선입니다. 발음·자연스러움·인물 유사성과 남은 배경 소음은 [README 샘플](../README.ko.md#카리나-샘플-듣기)을 직접 듣고 판단해 주세요.
